# Benchmark: vector-only vs Mycelium (vector + graph)

Same embeddings (bge-small, 384-d) and same FalkorDB vector index on both sides. The only difference is whether the graph is used. Synthetic org `graphhq`, generated by `seed/graphhq.py`. Reproduce with `PYTHONPATH=. uv run python -m eval.benchmark`.

| Task | Vector-only | Mycelium |
|---|---|---|
| Stale-fix trap: top-1 is the *current* fix | 0/12 (0%) | 12/12 (100%) |
| Stale-fix trap: top-1 is a superseded/broken fix | 12/12 (100%) | 0/12 (0%) |
| Cross-team / cross-project recall @1 | 12/12 (100%) | 12/12 (100%) |
| Question routing @1 (who should answer now) | 4/8 (50%) | 8/8 (100%) |
| Change impact: precision / recall of warned live agents | 0.5 / 0.56 | 1.0 / 1.0 |

- Tokens saved by correct cross-project recalls (estimated as 80% of the original session's tokens): **653,600** over 12 queries.
- Routing sent 8/8 questions to an agent that is live on the relevant component *right now*.
- Hybrid recall latency (vector KNN + 3 graph queries, local Docker, warm embeddings): p50 3.3 ms, p95 4.0 ms over 72 calls.

## Caveats (read these)
- The org, the planted stories and these cases were all written by us. The graph side benefits from relationships we chose to model, so treat the numbers as a demonstration of *mechanism*, not a general accuracy claim.
- Thresholds (similarity cut-offs, routing weights) were tuned while building on this same org. There is no held-out set.
- The vector baseline is deliberately simple (nearest neighbour). A strong RAG pipeline with re-ranking would do better on wording, but still cannot know that a fix was later superseded, who is live on which component, or what depends on what, because that information exists only as relationships.
